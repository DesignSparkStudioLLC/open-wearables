## Overview

S3 upload is **optional**. Small files import through the backend directly; configure S3 only if you want browsers to upload large Apple Health XML exports straight to object storage via presigned URLs.

The flow is deliberately simple and needs **no SNS, no event notifications, and no publicly reachable webhook**:

1. The frontend asks the backend for a presigned URL.
2. The browser uploads the file directly to S3.
3. The frontend calls `POST /api/v1/users/{user_id}/import/apple/xml/s3/complete` with the returned `file_key`.
4. The backend verifies the object exists and dispatches processing.

<Note>
  This works with **any S3-compatible object store** (AWS S3, MinIO, Railway Object Storage) - set `AWS_S3_ENDPOINT_URL` for non-AWS stores (see [Step 4](#step-4-configure-environment-variables)).
</Note>

## Prerequisites

- An account on your object-storage provider (AWS, or an S3-compatible store)
- AWS CLI installed (optional, but handy)

## Step 1: Create the bucket

<Steps>
  <Step title="Open S3 Console">
    Navigate to [AWS S3 Console](https://s3.console.aws.amazon.com/s3/) (or your provider's equivalent).
  </Step>

  <Step title="Create Bucket">
    Click **Create bucket** and configure:

    - **Bucket name**: Choose a unique name (e.g., `open-wearables-xml`)
    - **AWS Region**: Select your preferred region (e.g., `eu-north-1`)
    - **Block Public Access**: Keep all boxes checked (recommended - uploads use presigned URLs, not public access)
    - **Encryption**: Enable with SSE-S3 (recommended)
  </Step>
</Steps>

<Accordion title="Using AWS CLI">
```bash
aws s3api create-bucket \
  --bucket open-wearables-xml \
  --region eu-north-1 \
  --create-bucket-configuration LocationConstraint=eu-north-1
```
</Accordion>

## Step 2: Configure bucket CORS

The browser uploads **directly** to the bucket from the frontend origin, so the bucket must allow cross-origin `POST` requests.

<Steps>
  <Step title="Open CORS settings">
    Go to your bucket → **Permissions** tab → **Cross-origin resource sharing (CORS)** → **Edit**.
  </Step>

  <Step title="Add the policy">
    Replace `https://your-frontend-domain.com` with your dashboard origin:

```json
[
  {
    "AllowedHeaders": ["*"],
    "AllowedMethods": ["POST"],
    "AllowedOrigins": ["https://your-frontend-domain.com"],
    "ExposeHeaders": []
  }
]
```
  </Step>
</Steps>

<Warning>
  Without a matching CORS rule the browser will block the upload to S3. Use the exact frontend origin (scheme + host, no trailing slash).
</Warning>

## Step 3: Create IAM credentials

The app needs credentials that can sign presigned uploads, check that an object landed, and download it for processing.

<Steps>
  <Step title="Create an IAM user">
    In the [IAM Console](https://console.aws.amazon.com/iam/): **Users → Add users**, name it e.g. `open-wearables-app`, and enable **programmatic access** (access key).
  </Step>

  <Step title="Attach a least-privilege policy">
    A custom policy scoped to the bucket is enough (replace the bucket name):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AppleXmlUploads",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::open-wearables-xml",
        "arn:aws:s3:::open-wearables-xml/*"
      ]
    }
  ]
}
```

    - `s3:PutObject` - the presigned upload from the browser
    - `s3:GetObject` - the worker downloads the file to parse it, and the backend `HEAD`-checks it exists
    - `s3:ListBucket` - resolves `NoSuchKey` vs `AccessDenied` on the existence check
  </Step>

  <Step title="Copy the keys">
    Copy the **Access key ID** and **Secret access key** immediately (the secret is shown only once).
  </Step>
</Steps>

<Warning>
  Keep credentials secure and never commit them. On EC2/ECS, prefer an IAM role over static keys.
</Warning>

## Step 4: Configure environment variables

Add to your backend `.env`:

```bash
# S3 configuration
AWS_BUCKET_NAME=open-wearables-xml
AWS_REGION=eu-north-1
AWS_ACCESS_KEY_ID=your-access-key-id
AWS_SECRET_ACCESS_KEY=your-secret-access-key

# Only for S3-compatible stores (MinIO, Railway Object Storage). Leave unset for AWS S3.
# AWS_S3_ENDPOINT_URL=https://your-s3-compatible-endpoint
```

<Note>
  If any of `AWS_BUCKET_NAME`, `AWS_ACCESS_KEY_ID`, or `AWS_SECRET_ACCESS_KEY` is missing, the S3 endpoints return `503` and the platform falls back to direct upload for smaller files.
</Note>

## Step 5: Restart and verify

```bash
docker compose down
docker compose up -d
```

<Steps>
  <Step title="Test an upload">
    Upload an Apple Health XML export from the dashboard (large files use S3 automatically), or use the manual script from the [Apple XML Import Guide](/api-reference/guides/apple-xml-import).
  </Step>

  <Step title="Check backend logs">
    ```bash
    docker compose logs -f app celery-worker
    ```

    After the upload and the `.../s3/complete` call, you should see a `process_aws_upload` task dispatched and then completed.
  </Step>
</Steps>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Upload to S3 fails in the browser (CORS)">
    **Cause:** the bucket CORS rule does not match the frontend origin.

    **Fix:** verify the `AllowedOrigins` entry matches your dashboard origin exactly (scheme + host, no trailing slash) and includes `POST`.
  </Accordion>

  <Accordion title="Processing never starts">
    **Cause:** the `.../s3/complete` call did not reach the backend, or the object key does not belong to the user.

    **Fix:** confirm the frontend calls the complete endpoint after the upload, and that the `file_key` is the one returned by the presign step (`{user_id}/raw/...`). Check the worker logs for `process_aws_upload`.
  </Accordion>

  <Accordion title="Access Denied / 404 on the existence check">
    **Cause:** IAM permissions or wrong bucket/region.

    **Fix:** verify the policy grants `s3:GetObject` and `s3:ListBucket` on the bucket, the keys are correct, and `AWS_REGION` matches the bucket's region. For S3-compatible stores, confirm `AWS_S3_ENDPOINT_URL`.
  </Accordion>
</AccordionGroup>

## Security Best Practices

1. **Use IAM Roles**: On EC2/ECS, use IAM roles instead of static access keys
2. **Scope the bucket policy**: Grant only the three actions above on the single bucket
3. **Enable encryption**: SSE-S3 or SSE-KMS for data at rest
4. **Restrict CORS**: Allow only your real frontend origin(s)
5. **Rotate credentials**: Regularly rotate access keys
